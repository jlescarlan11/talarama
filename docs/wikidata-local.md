# Local Wikidata catalog trial

The default catalog is now Wikidata. `CATALOG_PROVIDER=wikidata` needs no API key; `tmdb` retains the earlier catalog integration and requires its server-only token. Existing local and explicit TMDB URLs, imports and retention tools remain available. Source licensing is still pending; the intended initial release remains noncommercial. Historical trial notes follow; current normal-app behavior is described below.

After a production build, `npm run preview:wikidata` starts `http://127.0.0.1:3000` with a fresh generated schema in the guarded loopback `_test` database. It creates one invented member and **no movie or review fixtures**. Google credentials are blank, no authentication bypass is installed, and no provider/image fixture preload is loaded. The ordinary `preview:local` command still offers the separate synthetic TMDB demonstration. Stop the owned preview before rebuilding on Windows.

The restored welcome/carousel, discovery grid, detail layout, themes and responsive behavior remain. Wikidata supplies real titles, original release years, runtime, genres and credits where available. Its short descriptions are not full synopses. Identity-linked Commons posters marked public domain or CC0 now appear where available; other cards keep the local artwork fallback. No popularity or ratings are invented. [Wikidata structured data is CC0](https://www.wikidata.org/wiki/Wikidata:Licensing); linked images have separate rights. See [poster loading and its limits](wikidata-posters-local.md).

## Normal app behavior

Normal Wikidata browsing now uses the same bounded background refresh, visible-page checks and public metadata outage recovery as the local trial. A valid HTTPS app origin or loopback HTTP origin in NEXTAUTH_URL enables it; TALARAMA_MOVIE_SYNC=0 disables refresh and disk backup. Builds and the TMDB provider never start the worker. Public metadata defaults to the ignored .superpowers/wikidata-cache directory; an empty TALARAMA_DISCOVERY_CACHE_DIR disables disk persistence, and arbitrary paths are rejected. Read-only or ephemeral hosts retain in-memory operation; durable recovery across host restarts requires persistent storage. No account, diary, library, image URL or artwork credit is stored in this cache.

Normal discovery keeps films whose verified artwork is missing and renders the existing placeholder. This prevents sparse licensed posters from exhausting the continuation budget and surfacing a false provider outage. The explicit disposable Wikidata preview retains its poster-focused selection. Wikipedia copyrighted thumbnails are available in normal mode with TALARAMA_WIKIPEDIA_POSTERS=1; source labels and transient-only storage remain enforced. Real upstream outages still require a previously successful public metadata snapshot for recovery; uncached data can remain temporarily unavailable. Historical trial notes below describe their original preview scope.

Type checking runs next typegen before tsc so a fresh CI checkout has Next.js image and route declarations.

## Identity and preservation

The additive `20261019190000_wikidata_identity` migration creates `ExternalMovieIdentity` only. It never changes existing Movie IDs, metadata, account links, reviews, library records or dates. A validated Q ID maps to one local movie per provider. Authenticated save/log intent imports metadata atomically; concurrent or repeated saves reuse that movie. Read-only browsing never imports it. An identically titled legacy/TMDB movie remains separate until an independently reviewed mapping is authorized. Existing local IDs continue to resolve.

Migration and logical backup/restore tests use seeded disposable schemas. They compare legacy IDs, account tokens, relationships, review text and exact `2020-02-29T23:30:00.000Z` timestamps. No populated development database was migrated and no real member record was changed. Existing privacy, moderation, diary retries, watchlist removal on logging and mutation quotas continue to use their original services.

## Query boundaries

- The homepage and unfiltered discovery start with recent films with verified posters: this UTC year and the previous two years, newest first by original release year. Each year starts with up to 240 explicitly typed, coverage-ranked candidates with at least one sitelink, then follows live SPARQL continuation in 48-candidate batches. There is no fixed 720-candidate cutoff. The continuation key is the last language-coverage count and Q ID, ordered by descending count and lexical identifier; every returned cursor must advance. An entire recent year is traversed before moving to the previous year or the older archive. Within each loaded batch, Q ID is the stable display tie-breaker; earlier same-year batches stay ahead of later batches. Current-year metadata loads first, and further batches/years load only when a requested page or its lookahead needs them. Dates are bounded before tomorrow UTC; normalized first release years exclude older regional re-releases. This is source-driven browsing, not an exhaustive release calendar or popularity chart. Artwork is verified lazily in 12-film batches, only far enough for the requested page plus one verified lookahead. Batch promises are coalesced in a five-minute in-memory selection; metadata is cached for an hour, fetched at most 50 IDs at a time with two concurrent requests. The local background worker warms an additional discovery page on each minute sweep, even with no browser activity, and rechecks the newest page hourly. Minute visible-page checks remain active in the explicit local preview. New source entries are picked up after cache expiry; continuation requires no manual movie list or imports. Pagination uses `hasMore` and lower-bound totals until the final page; it never claims an exact total before scanning the source. Up to four fresh continuation batches may load per request, shared with the older archive; cached progress survives retries, including the next automatic page check. Failed metadata requests and nonadvancing cursors remain retryable. The existing 500-page UI safety bound and bounded metadata cache remain; this removes the recent candidate cutoff without claiming unlimited resource use. Total poster failure remains retryable. No catalog/member rows are written by browsing.
- After the recent selection, default browsing appends older films and classics with verified posters. Its separate, lazy Action API query selects up to 240 explicitly typed films with English labels ordered by incoming links. Normalized first release years must predate the recent window; the older selection is then ordered by release year and Q ID, with recent IDs excluded. Older metadata and artwork use the same hour/five-minute cache policy, 50-ID/two-request metadata bounds, and 12-film artwork batches. The older source is fetched only when the requested page or its lookahead needs it, so ordinary homepage reads retain the recent path. A failed older-source request surfaces a retry instead of a false final page. These opening selections are bounded. After them, default browsing follows the Action API continuation offsets in 48-candidate batches of older films. Each batch is ordered by release year, while the opening recent/classics selections and previously returned batch order stay ahead of new additions. The full continued archive is therefore not globally chronological. IDs seen in prior selections/batches are excluded and every returned result has a verified poster. Discovery does not stop at the former 303-film snapshot.
- Continued discovery uses a separate bounded 512-entry cache (metadata one hour, poster selections five minutes). In the explicit live loopback preview, public discovery metadata and continuation keys also persist locally as described below; poster selections remain in memory. At most four new continuation metadata batches load per request; cold deep-page jumps or unusually sparse batches may need a retry, which reuses cached progress. Normal Next-page browsing fetches more candidates only as needed for a full page and a verified lookahead. Failed or malformed continuation loads are not cached as final pages. Cursor progress is validated, and the existing 500-page application bound plus a 10,000-candidate source-offset bound remain; this is not an exhaustive archive claim.
- Explicit genre browsing and title search use the official Action API, ordered by incoming links, with 12 results per page and a 500-page application limit. Incoming links are coverage, not popularity. Year, genre and title filters continue to reach beyond these default selections.
- Release-year queries use bounded SPARQL. Year browsing uses explicit film statements (`Q11424`) or the selected genre statement; it is not an exhaustive subclass traversal. Title-plus-year searches consider the first 100 matching titles. These limits are disclosed beside the filters.
- The earliest nondeprecated precise publication year is used. Regional re-releases do not change the displayed original year; excluding these or blocked entries can make pages shorter than 12. Next follows the upstream candidate page rather than claiming exhaustive totals.
- Public requests have a descriptive User-Agent, fixed HTTPS endpoints, redirect refusal, a 20-second request/body timeout, an 8MiB body limit, bounded coalescing caches and 429 cooldown. Oversized entity batches are cancelled and split sequentially into smaller requests while preserving the two-request concurrency ceiling; a single entity over the limit still fails. Wikidata full-detail metadata and Commons artwork use separate per-process caches; decorated movie responses are not persisted in Next's shared cache, allowing artwork recovery after transient failures. A preview/test process owns its cache instance. Interactive Action API reads omit `maxlag`, as permitted by [MediaWiki guidance](https://www.mediawiki.org/wiki/Manual:Maxlag_parameter), so query-service replication lag does not unnecessarily block entity reads. No member state enters shared metadata caches.
- Saved detail snapshots and per-member library state remain available during provider outages. Unconfigured real Google OAuth is still an acceptance gate.

## Automatic local refresh

`npm run preview:wikidata` now starts a background worker through Next instrumentation. While that owned loopback server runs, it checks every minute, refreshes public movie metadata and poster validation with a one-hour freshness target, and prefetches one additional verified discovery page per sweep. On its first run it starts at page 1, advances without navigation, and rechecks page 1 hourly without losing its advancing position. A failed read retains the same page for the next sweep; calls coalesce, with at least a minute between completed attempts. On reaching the current end or the existing page-500 application bound, it pauses until the next hourly head check, then begins another scan if more results exist. Public source availability, cache eviction and the existing bounded continuation budget can delay deep or sparse pages. Prefetch shares the browsing cache and bypasses the full-detail queue for unseen films. The public discovery metadata, continuation keys, page frontier and scheduling state persist in `.superpowers/wikidata-cache/discovery-v1.json`, outside the disposable preview database schema. Restarting the same preview resumes the next page; an overdue hourly head check runs before returning to that frontier. Original metadata expiry times survive restarts, so stale metadata is fetched again. Artwork URLs and credits are never written to this cache: poster availability is revalidated after restart before movies appear. No movie/member rows are imported. Saved-mapping read failures do not prevent discovery from advancing. Each sweep reads at most 12 saved WIKIDATA identity links and refreshes at most 12 due movies with at most two concurrent detail loads. Larger libraries rotate through bounded batches; recently browsed films also join a transient 512-film cache. Closing the preview ends the worker. It does not install an OS task or run when localhost is stopped.

Visible pages also check for updates every minute in the explicit local preview. Server-rendered homepage, detail and diary views update in place; discovery silently refetches its current URL, and public cards recheck eligibility without remounting valid report/spoiler controls. Filters, pagination, scroll, focus and unsaved diary fields stay intact. Polling pauses while the tab is hidden, offline or saving, catches up on resume, and does not overlap slow reads. Discovery and the homepage retain their last successful visible movie data during provider outages. Privacy/resume/publication checks still immediately discard previously displayed public content; withdrawn or failed public reads clear it. No hard reload or user action is needed for new metadata to appear. Source freshness remains the hourly target above; client checks normally read server caches.

Cold saved lists can show their saved snapshot while a refresh runs. Existing database movie snapshots, stable IDs, external mappings, genre links, accounts, viewing dates, reviews, ratings and member state are never rewritten by synchronization. Unmapped legacy movies are not guessed by title or merged. No member data is sent to Wikimedia; the worker reads public Q IDs only. Decorated full-detail responses and copyrighted thumbnail URLs use transient server/browser memory. Successful public detail metadata and its public artwork source names also have a whitelisted local backup in the same bounded file, without image URLs, credits or member fields. The separate discovery file contains only whitelisted public metadata, public artwork source names/article titles, continuation keys and worker scheduling state; it excludes local identities, member data, image URLs and credits. There is no new persistent browser storage or database write.

Source outages retain the last successful metadata. The explicit local preview also saves each successful default discovery page as a whitelisted public snapshot in the same bounded cache file. On timeout, rate limit or temporary Wikidata unavailability, homepage/default discovery can return that exact cached page, including its original Q IDs, order and pagination. This works after a restart and date change. The API marks this response `stale: true`; it does not rewrite the disk snapshot or renew metadata expiry. One shared retry deadline limits new attempts to once per minute, and the existing visible-page checks replace cached results after recovery. Background discovery keeps its frontier and retries until a fresh page succeeds. Missing pages and other searches/filters never receive a substituted default page; invalid or blocked data is not masked by this fallback. Artwork is revalidated separately. A temporary artwork-source failure may retain the running process's last verified poster; after a restart, unavailable artwork uses the original placeholder while cached titles remain visible. Image URLs and credits remain memory only. Successful source responses, including removed artwork or an empty page, replace old snapshots. The existing combined 512-entry/16MiB bound covers metadata, continuations, page snapshots and detail backups. Artwork outages accept fresh details while preserving the last working poster and retrying on a later minute sweep; successful absent/revoked artwork removes the image. Existing rate-limit cooldowns remain in force. No TMDB token is needed. The worker requires the explicit `TALARAMA_LOCAL_PREVIEW=wikidata` loopback configuration set by the preview command; it stays off in builds, ordinary unconfigured servers and hosted environments. The preview launcher explicitly enables the ignored cache directory; fixtures, ordinary servers and builds do not enable persistence. File reads are schema-validated and bounded to 16MiB/512 selections; writes use an atomic temporary-file replacement. Invalid or unreadable files fall back to source reads, and write failures keep memory discovery active. Nonadvancing cached cursors are discarded. Closing the preview retains this public cache while removing only its disposable schema. Licensing remains pending, and no push or deployment is involved.

## Search and filtered discovery outage fallback

In the explicit local Wikidata preview, successful title searches and year/genre discovery pages now back up their exact public results. The cache index uses a digest of the trimmed title, genre, year and page; raw search text is not stored as an index. Each combination is separate from default discovery and other searches. Temporary source failures, timeouts and rate limiting can show that same page after a restart, including a confirmed empty result. Uncached combinations retain the existing unavailable behavior, and invalid inputs or malformed live responses do not become cache successes. Pagination, source ordering, lower-bound year totals and capped search page counts retain their existing semantics.

Live reads remain preferred. Only a successful upstream metadata load replaces a backup; a stale or still-fresh in-memory read does not renew it. Failed searches retry at most once per minute per combination, respecting upstream rate limits. The existing visible-page polling reloads the current URL and replaces fallback results when Wikidata recovers, preserving unapplied filter drafts and page state. Artwork is revalidated independently; verified source-specific memory artwork can survive a temporary failure, while a cold restart uses the original placeholder if artwork is unavailable. Search backups share the existing 512-entry/16MiB public-only cache bounds. Image URLs, artwork credits, member state and local IDs remain excluded. No movie import, database migration, layout or styling change is involved.
