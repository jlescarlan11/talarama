# Local Wikidata catalog trial

The default catalog is now Wikidata. `CATALOG_PROVIDER=wikidata` needs no API key; `tmdb` retains the earlier catalog integration and requires its server-only token. Existing local and explicit TMDB URLs, imports and retention tools remain available. Source licensing is still pending; the intended initial release remains noncommercial. Nothing has been pushed or deployed.

After a production build, `npm run preview:wikidata` starts `http://127.0.0.1:3000` with a fresh generated schema in the guarded loopback `_test` database. It creates one invented member and **no movie or review fixtures**. Google credentials are blank, no authentication bypass is installed, and no provider/image fixture preload is loaded. The ordinary `preview:local` command still offers the separate synthetic TMDB demonstration. Stop the owned preview before rebuilding on Windows.

The restored welcome/carousel, discovery grid, detail layout, themes and responsive behavior remain. Wikidata supplies real titles, original release years, runtime, genres and credits where available. Its short descriptions are not full synopses. Identity-linked Commons posters marked public domain or CC0 now appear where available; other cards keep the local artwork fallback. No popularity or ratings are invented. [Wikidata structured data is CC0](https://www.wikidata.org/wiki/Wikidata:Licensing); linked images have separate rights. See [poster loading and its limits](wikidata-posters-local.md).

## Identity and preservation

The additive `20261019190000_wikidata_identity` migration creates `ExternalMovieIdentity` only. It never changes existing Movie IDs, metadata, account links, reviews, library records or dates. A validated Q ID maps to one local movie per provider. Authenticated save/log intent imports metadata atomically; concurrent or repeated saves reuse that movie. Read-only browsing never imports it. An identically titled legacy/TMDB movie remains separate until an independently reviewed mapping is authorized. Existing local IDs continue to resolve.

Migration and logical backup/restore tests use seeded disposable schemas. They compare legacy IDs, account tokens, relationships, review text and exact `2020-02-29T23:30:00.000Z` timestamps. No populated development database was migrated and no real member record was changed. Existing privacy, moderation, diary retries, watchlist removal on logging and mutation quotas continue to use their original services.

## Query boundaries

- The homepage and unfiltered discovery start with recent films with verified posters: this UTC year and the previous two years, newest first by original release year, with Q ID as a stable tie-breaker. A live SPARQL query selects up to 240 explicitly typed films with at least 10 language sitelinks, ranked by language coverage. Dates are bounded before tomorrow UTC; normalized metadata excludes older regional re-releases. This is a selection, not an exhaustive release calendar or popularity chart. Candidates are ordered before poster checks. Artwork is verified lazily in 12-film batches, only far enough for the requested page plus one verified lookahead. Batch promises are coalesced in a five-minute in-memory selection; metadata is cached for an hour, fetched at most 50 IDs at a time with two concurrent requests. Pagination uses `hasMore` and lower-bound totals until the final page; it never claims an exact total before scanning the selection. Total poster failure remains retryable. No catalog/member rows are written by browsing.
- After the recent selection, default browsing appends older films and classics with verified posters. Its separate, lazy Action API query selects up to 240 explicitly typed films with English labels ordered by incoming links. Normalized first release years must predate the recent window; the older selection is then ordered by release year and Q ID, with recent IDs excluded. Older metadata and artwork use the same hour/five-minute cache policy, 50-ID/two-request metadata bounds, and 12-film artwork batches. The older source is fetched only when the requested page or its lookahead needs it, so ordinary homepage reads retain the recent path. A failed older-source request surfaces a retry instead of a false final page. These opening selections are bounded. After them, default browsing follows the Action API continuation offsets in 48-candidate batches of older films. Each batch is ordered by release year, while the opening recent/classics selections and previously returned batch order stay ahead of new additions. The full continued archive is therefore not globally chronological. IDs seen in prior selections/batches are excluded and every returned result has a verified poster. Discovery does not stop at the former 303-film snapshot.
- Continued discovery uses a separate bounded 512-entry in-memory cache (metadata one hour, poster selections five minutes). At most four new continuation metadata batches load per request; cold deep-page jumps or unusually sparse batches may need a retry, which reuses cached progress. Normal Next-page browsing fetches more candidates only as needed for a full page and a verified lookahead. Failed or malformed continuation loads are not cached as final pages. Cursor progress is validated, and the existing 500-page application bound plus a 10,000-candidate source-offset bound remain; this is not an exhaustive archive claim.
- Explicit genre browsing and title search use the official Action API, ordered by incoming links, with 12 results per page and a 500-page application limit. Incoming links are coverage, not popularity. Year, genre and title filters continue to reach beyond these default selections.
- Release-year queries use bounded SPARQL. Year browsing uses explicit film statements (`Q11424`) or the selected genre statement; it is not an exhaustive subclass traversal. Title-plus-year searches consider the first 100 matching titles. These limits are disclosed beside the filters.
- The earliest nondeprecated precise publication year is used. Regional re-releases do not change the displayed original year; excluding these or blocked entries can make pages shorter than 12. Next follows the upstream candidate page rather than claiming exhaustive totals.
- Public requests have a descriptive User-Agent, fixed HTTPS endpoints, redirect refusal, a 20-second request/body timeout, an 8MiB body limit, bounded coalescing caches and 429 cooldown. Oversized entity batches are cancelled and split sequentially into smaller requests while preserving the two-request concurrency ceiling; a single entity over the limit still fails. Wikidata metadata and Commons artwork use separate per-process caches; decorated movie responses are not persisted in Next's shared cache, allowing artwork recovery after transient failures. A preview/test process owns its cache instance. Interactive Action API reads omit `maxlag`, as permitted by [MediaWiki guidance](https://www.mediawiki.org/wiki/Manual:Maxlag_parameter), so query-service replication lag does not unnecessarily block entity reads. No member state enters shared metadata caches.
- Saved detail snapshots and per-member library state remain available during provider outages. Unconfigured real Google OAuth is still an acceptance gate.

## Automatic local refresh

`npm run preview:wikidata` now starts a background worker through Next instrumentation. While that owned loopback server runs, it checks every minute, refreshes public movie metadata and poster validation with a one-hour freshness target, and warms the opening discovery selection hourly. Each sweep reads at most 12 saved WIKIDATA identity links and refreshes at most 12 due movies with at most two concurrent detail loads. Larger libraries rotate through bounded batches; recently browsed films also join a transient 512-film cache. Closing the preview ends the worker. It does not install an OS task or run when localhost is stopped.

Visible pages also check for updates every minute in the explicit local preview. Server-rendered homepage, detail and diary views update in place; discovery silently refetches its current URL, and public cards recheck eligibility without remounting valid report/spoiler controls. Filters, pagination, scroll, focus and unsaved diary fields stay intact. Polling pauses while the tab is hidden, offline or saving, catches up on resume, and does not overlap slow reads. Discovery and the homepage retain their last successful visible movie data during provider outages. Privacy/resume/publication checks still immediately discard previously displayed public content; withdrawn or failed public reads clear it. No hard reload or user action is needed for new metadata to appear. Source freshness remains the hourly target above; client checks normally read server caches.

Cold saved lists can show their saved snapshot while a refresh runs. Existing database movie snapshots, stable IDs, external mappings, genre links, accounts, viewing dates, reviews, ratings and member state are never rewritten by synchronization. Unmapped legacy movies are not guessed by title or merged. No member data is sent to Wikimedia; the worker reads public Q IDs only. Refreshed metadata and copyrighted thumbnail URLs use transient server/browser memory, with no new persistent browser storage or database writes.

Source outages retain the last successful metadata. Artwork outages accept fresh details while preserving the last working poster and retrying on a later minute sweep; successful absent/revoked artwork removes the image. Existing rate-limit cooldowns remain in force. No TMDB token is needed. The worker requires the explicit `TALARAMA_LOCAL_PREVIEW=wikidata` loopback configuration set by the preview command; it stays off in builds, ordinary unconfigured servers and hosted environments. Licensing remains pending, and no push or deployment is involved.

## Measured evidence

On 2026-10-19, public reads without fixture transport returned Women Make Film, Iron Man 2 and Harry Potter and the Philosopher's Stone in discovery; title search and title/year search returned Inception (Q25188, 2010). Its detail returned Christopher Nolan. Year/Science Fiction and year-only queries returned real 2010 films. Discovery/search/detail took about 2–4seconds; an uncached year-only read took about20seconds. Public endpoint availability and latency can vary; failures expose retry and saved snapshots.

On 2026-10-20, the new default returned 42 films with verified posters across four pages from 2024–2026, including Project Hail Mary, The Odyssey and Avatar: Fire and Ash. The uncached selection took about 17 seconds including metadata and artwork verification; later pages reuse the bounded selection. The Wikipedia poster preview remains local and transient; licensing remains pending.

Later on 2026-10-20, expanding the candidate pool to 240 and lowering the language-coverage threshold to 10 returned 169 verified-poster films across 15 pages. A live loopback check walked every page and confirmed unique Q IDs, descending release years (2026–2024), poster availability, and zero movie, external-identity or diary rows created by browsing. Lazy page loading reports `hasMore` rather than prematurely claiming a total. All 137 unit tests, 54 disposable-database integration tests, both catalog/poster browser journeys, lint, type checking and the production build passed. The catalog browser fixture checks six pages and terminal Next-button behavior.

One independent read-only review found an invented preview movie leak, year pagination beyond the allowed page500, and missing Wikidata provenance in the homepage outage fallback. All were addressed with regressions observed failing then passing. The latter two were regraded as important because they broke the promised filter/navigation boundary and source attribution respectively.

Final local test counts and localhost evidence are recorded in the implementation plan. Historical portfolio screenshots still show synthetic fixtures and retain their original labels.

The older-film extension was verified locally on 2026-10-20 with 303 verified-poster films across 26 pages: 170 recent films and 133 older films, spanning 2026–1939.
